Demux, repair and tag edits peak within 10 MiB of their small-file figure at 4 GiB. Remux grows from about 50 to 65-85 MiB. **Packaging is the one area that is not flat:** the two 4 GiB inputs peak at 173 and 189 MiB against 50 MiB for the 27 MB file. The packager builds each segment before it writes it, which is the likely cause (the high bitrate of these test files makes one segment large), but this unit did not separate that from other causes; the figure does not grow with the number of segments in the live-mode soak of the packaging stage (106 MiB plateau over 2 hours). Open item: confirm and, if it is the segment buffer, write segments through a bounded buffer.

36 of the 1,000+ files read more than 1 MiB. The ISO BMFF and Matroska cases read about as much as ffprobe does. The MPEG cases below the documented bound are the front and tail windows; **four transport streams read well past the documented bound and are an open item** (foxksaz.ts 25.4 MB of 30.5 MB, vid_0x80.ts 12.1 MB of an 8.4 MB file, HD-h264.ts 11.5 MB, test-ebu-422.40000.pakets.ts 9.1 MB): ffprobe 7.0.2 reads 6.1-14.3 MB over HTTP on the same four, so they are unusual streams, but ours reads some bytes twice (more bytes than the file holds on vid_0x80.ts) and should not. The pinned oracle figures in [io-oracle-baseline.tsv](../io-oracle-baseline.tsv) are unchanged: same tool versions as 0.2.

**AVI changed in this stage:** the header list is read through a 32 KiB front cache and a read-ahead window, so a probe makes 10 to 50 reads of the file instead of about 100 (tagged-mpeg4-mp3.avi 99 to 15 reads, GoneNutty.avi 99 to 8, the 4.6 GB OpenDML file 50 after) and the avi-probe row went from 1.95x to 0.52x of the fastest comparator. Over HTTP the median probe is now 114,509 B in 9 requests (before: 4,559 B in 32 requests; the whole table is above). It trades bytes for round trips; an 8 KiB window gave 45 KB in 10 requests and is left as a follow-up because the speed rows were taken with this build.
