# OneMedia speed rows, version 0.3 (x64)

Three publishable runs under the exclusive bench queue, one per filtered group, 3 repetitions (tools 3), run on the build of 2026-11-02 (main 33c568d plus the bench rows). Groups: A `mp4-mux`, `mp4-remux`, `mkv-mux`; B `tagw-id3`, `tagw-flac`, `tagw-ilst`, `tagw-riff`, `tagw-mkv`; C `remux-mem`, `playable`. Comparators: SharpMP4 0.3.2, TagLib# 2.3.0, ATL.NET 7.19. Method: [docs/bench.md](../bench.md).

Notes

- Each group ran as its own job under the exclusive benchmark queue, alone on the machine. Load before/during/after is in each group's header below; the load average also counts the shell steps around the run.
- Tag-write rows edit the same four common fields (title, artist, album, comment) of a file held in memory; method and the difference in work per implementation are in [docs/bench.md](../bench.md). The ratio is against TagLib#, the fastest managed comparator on every file here; ATL.NET is 1.2x to 18x slower than TagLib# (its ratio column), least on WAV and most on APE-tagged MP3.
- **`tagw-mkv` is not a comparison of breadth**: neither comparator is a Matroska writer in practice. ATL.NET fails on both files (NullReferenceException) and TagLib# fails on `test1.mkv` ("Invalid EBML format"), so the row has one file, `h264-two-audio-tags.mkv`, where TagLib# reads and writes it. The ratio there is 0.99x (OneMedia 121.8 us, TagLib# 123.4 us) and the bar is met on this machine.
- Rows `mkv-mux`, `remux-mem` and `playable` have no managed comparator (no managed Matroska writer; no managed remuxer), so they pass; the times next to ffmpeg 7.0.2 and mkvmerge 103.0 are information. mkvmerge exits 1 on these files (warnings about the input) and its time is still the whole run.
- `remux-mem`: OneMedia remuxing the two files over 4 GiB (a 4.08 GiB MP4 with the movie box at the end, a 4.14 GiB Matroska file) into MP4 and Matroska on disk peaks at 62 to 95 MiB resident, process start-up included (baseline about 29 MiB); ffmpeg `-c copy` to Matroska peaks at 31 MiB. Allocation per run is 2 to 25 MiB.
- `playable` (MakePlayable for the generic MP4 profile on a 0.2 MiB Matroska file) takes 160 ms here against 7.6 ms for ffmpeg (information). An indicative run on the same machine of the build before the writer fixes took 9.6 ms; the difference is in what the new save path does (flushing the temporary file to disk before the rename), which a 0.2 MiB file notices and a large one does not. It is reported, not tuned.
